## 一、全体アーキテクチャ

一言で言うと：PDFに対する「持ち込み可の試験」方式の質問応答——文書を分割してベクトル化し、ベクトルDBに保存。ユーザーが質問すると、意味的に最も関連する断片を検索し、その断片と質問を一緒に大規模言語モデルに渡して、実際の原文に基づいて回答させる。でっち上げさせない。

```
PDF → チャンク分割 → ベクトル化(embedding) → ベクトルDB(Chroma)に保存
                                              │
ユーザーの質問 → ベクトル化 → 類似度検索(上位k件) → 関連度フィルタ → プロンプトに組み込み → LLMが回答生成
```

中核となる2ファイル：`rag_pipeline.py`（RAGの5ステップ）、`main.py`/`app.py`（それぞれCLI版・Web版の外殻で、同じpipelineを呼び出す）。

## 二、設計判断のタイムライン

判断した時期のおおよその順に並べている（モジュール別ではない）——そうすることで「その時点でなぜその判断をしたか」が見える。

### D1（2026-10-01）embeddingモデルは多言語対応のものを選ぶべき。「デフォルト／定番」だけで選んではいけない

最初使っていた `all-MiniLM-L6-v2` は英語中心で学習されたモデルで、日本語文書の検索が機能しなかった（「彼の名前は」と聞くと「わからない」と回答——しかし原文の最初の一文に氏名が明記されているにもかかわらず）。`paraphrase-multilingual-MiniLM-L12-v2` に変更して正常化。

**教訓**：embeddingモデルは文書の実際の言語と一致させなければならない。間違えても**エラーは出ず、検索が静かに失敗するだけ**——意識的にテストしないと見つけにくい落とし穴。詳細は [bug-log.ja.md #4](bug-log.ja.md)。

### D2（2026-10-01）ベクトルDBは「既存なら読み込み、なければ新規作成」の判定を入れるべき

当初の `build_vector_store()` は毎回無条件に全embeddingを再計算し、ベクトルDBを再構築していた。`persist_directory` が既に存在し空でないかを先にチェックし、あれば直接読み込むように変更——重複計算のコストを省いた。詳細は [project-notes.ja.md 四-5](project-notes.ja.md)。

この判断は後にD7のプライバシーバグに間接的につながった（後述）。「既存の接続／collectionを再利用する」ことと「セッションごとに互いを隔離する」ことは実は相反する要求で、当時は前者しか意識していなかった。

### D3（2026-10-01）回答生成モデル：Claude → Gemini（「元々の設計」より無料枠を優先）

プロジェクトは当初Claude（`ChatAnthropic`）で回答生成する設計だったが、key申請には事前チャージが必要。無料で学習・テストを続けるため、Google Geminiに切り替えた。**Claude関連のコードは削除せず、コメントアウトで保持**——これは単に手を抜いたのではなく意図的な判断で、プロバイダ間の原理は完全に同じ（どちらも「クラウドの大規模モデルを呼んで理解＋生成する」）ため、切り替えコストは低く保つべきという考えから。詳細は [project-notes.ja.md 三](project-notes.ja.md)。

Groq、Ollama（完全ローカル）、Hugging Face Inference APIなど他の無料／低コスト案も調査済みで記録してあるが、切り替えの必要がなく未実施。

### D4（2026-10-26）モデル選定は「速度 vs 精度」の定量的トレードオフであり、思いつきの変更ではない

`gemini-3.8-flash` の無料枠は1日20回しかなく、しかも枠の上限に近づくほど応答が徐々に遅くなる現象があった（150～367秒）。`gemini-3.1-flash-lite` に変更すると速度は数十倍向上（平均4.76秒）したが、代償として**精度が実測で約85%まで下がった**——13問＋別文書での6問の評価で検証済みで、失敗パターンは「同じ段落に複数の情報ポイントがあり、モデルがそのうちの一つを時々取りこぼす」ケースに集中している。

これは現時点でプロジェクト内で唯一、**定量的な実験を経て、トレードオフがあることを明確に認めた上での設計判断**であり、「変えたら良くなった気がする」ではない。詳細は [project-notes.ja.md 四-15](project-notes.ja.md)。

### D5（2026-10-26）関連度フィルタ：embeddingプロバイダごとに閾値を分けて設定し、固定値を書かない

モデルが「文書内に答えが存在しない」場合にでっち上げるのを防ぐため、関連度スコアによるフィルタを追加した：検索された断片のスコアが基準に達していなければ、LLMを呼ばずに「関連する内容が見つかりませんでした」を直接返す。

実測の結果：同じ「関連している」内容でも、ローカルのHuggingFace embeddingが出すスコアの桁（16～18）とクラウドのGoogle embeddingが出すスコアの桁（0.69～0.76）はまったく異なるスケールだった（しかもローカルモデルはスコアが高いほど無関連、クラウドモデルはスコアが低いほど関連——「方向」すら逆）。そのため閾値はプロバイダ別のテーブル（辞書）にし、グローバルな定数一つでは済ませなかった。環境変数での上書きも残してある。詳細は [project-notes.ja.md 四-10](project-notes.ja.md)。

### D6（2026-10-26）ベクトルDBは「セッション」単位で隔離が必須。デフォルトのcollection_nameは安全ではない

`Chroma.from_documents()` は `collection_name` を指定しない場合デフォルト値が固定で `'langchain'` になる。`persist_directory=None` のメモリモードでは、同一プロセス内で連続呼び出す（Web版はユーザーが新しいPDFをアップロードするたびに1回呼ぶ）と、同じcollectionにデータが追加され続け、クリア・再構築されない——**異なるユーザーがアップロードした文書の内容がベクトルDB内で混線する**、単なる機能バグではなく実際のプライバシー漏洩リスクだった。

修正方法は毎回の呼び出しに `collection_name=f"session-{uuid.uuid4()}"` を渡し、毎回独立したベクトル空間を強制することだった。この判断から得られる教訓は：D2の「既存ベクトルDBを再利用する」という最適化の発想は、「同じ文書を繰り返し処理する場合は再利用してよい」のと「異なるセッション／文書は必ず隔離すべき」という2つのシナリオを明確に区別しなければならず、同じデフォルト挙動で両方に対応してはいけないということ。詳細は [bug-log.ja.md #8](bug-log.ja.md)。

### D7（2026-10-26）chunk_sizeは思いつきのデフォルト値ではなく、実測で調整した値

デフォルトの `chunk_size=500` は最適値ではなかった。「同一文書でパラメータを変える」と「同一パラメータで文書を変える」の2つの比較実験を行い（この過程でD6のプライバシーバグを偶然発見し、最初の1回分のデータは破棄してやり直した）、最終的にデフォルト値を `800` に変更、テストで満点を獲得した。実験設計・データ・限界についての議論の全体は [parameter-tuning.ja.md](parameter-tuning.ja.md) に記載、ここでは繰り返さない。

**未実施の今後の研究課題**（やることリストではなく課題として記録）：文字数で固定的に分割する方式は、短い文書／特定フォーマットの文書にとって最適とは限らない。「カスタム分割優先順位」「プロジェクト単位での分割」「セマンティックチャンキング」「短文書は分割しない」という4つの適応的な方式を議論し、検討の結果「現在のフォーマットに特化したシンプルなルール」が最もコストパフォーマンスが良いと判断、セマンティックチャンキングは「牛刀割鶏」と判断し、現時点では未実施。詳細は [project-notes.ja.md 四-17](project-notes.ja.md)。

### D8（2026-10-26）テスト方針：ネットワークに触れない純粋なロジックのみをテストし、実際のLLM呼び出しは意図的に自動テストしない

単体テストは `split_into_chunks()`、`_build_prompt()`、閾値テーブル、「見つかりません」のメッセージ文言といった決定論的なロジックをカバーする。**意図的に** `ask_question()`／`build_qa_chain()` など実際にGemini APIを呼び出す関数はカバーしていない——理由は明確で、CIで安全に公開できるkeyがない、呼び出し結果の不確実性が高い、無料枠を消費してしまう、という3点。これは「何をテストし、何をテストしないか」の境界線の引き方であり、単なるテスト漏れではない。理由は [test-cases/unit-test-cases.md](../test-cases/unit-test-cases.md) に明記。

### D9（2026-10-27）CI/CD：テストはデプロイの前提ゲートであり、イメージは`:latest`ではなく一意なタグを使わなければならない

独立しているが関連する2つの設計判断：
1. `test` job（lint＋単体テスト）が通らなければ `build-and-deploy` job は発火しない——品質ゲートとデプロイ自動化は同じパイプラインに組み込まれていなければならず、分離してはいけない。
2. イメージタグは `:latest` だけに頼ってはいけない：Azure Container Appsが「新しいイメージを取得すべきか」を判断する根拠は、**イメージアドレスの文字列自体が変化したかどうか**であり、タグの裏側の内容が変わったかどうかはチェックしない。固定タグでは「GitHub Actionsはずっと緑色で成功表示なのに、Azureは実際には最初のデプロイの古いイメージをずっと動かし続けている」という事態を招く——非常に見えにくい「偽の成功」の罠で、実際に発生した（[bug-log.ja.md #10](bug-log.ja.md) 参照）。修正案は「日付＋commit短縮SHA」形式の一意なタグを追加で打ち、実際のデプロイにはそちらを使うこと。

### D10（2026-10-26）ログレベル分け：内部状態はlogger、ユーザー向けの画面文言はprintのまま残す

`rag_pipeline.py` 内の内部処理ステップを表す出力は `print` から `logger.info`／`logger.warning` に変更したが、`main.py` 内の本当にCLIユーザーに向けた対話文言（質問、エラー表示）は**意図的にprintのまま残し**、今回の改修範囲に含めなかった——それはユーザーインターフェースであり内部の状態ログではなく、両者の役割は異なるため同じ仕組みを使うべきではないという考えから。詳細は [project-notes.ja.md 四-14](project-notes.ja.md)。

### D11（2026-10-26）アクセス制御はオプション機能として実装し、すべてのデプロイに設定を強制しない

WebデモのパスワードゲートはオプションでEnvironment変数 `APP_PASSWORD` を使って実装：設定すれば検証が有効になり、設定しなければ完全に影響を受けず、ローカル開発では今まで通りそのまま使える。これによりローカル開発体験と「外部に公開する前には一段階ゲートを入れる」という要求が衝突せず、2系統のコードパスを維持する必要もない。詳細は [project-notes.ja.md 四-9](project-notes.ja.md)。

### D12（検討中、未実装）複数人の履歴書スクリーニング機能：構造化フィルタ＋意味的な再確認のハイブリッド構成

これは現在まだ議論段階で、コードはまだ書いていない新しい方向性：プロジェクトを「単一文書への意味的質問応答」から「複数の履歴書に対する条件スクリーニング」（例えば「Javaを5年学び、プロジェクトを独立して担当できる人を探す」）へ拡張する。

**核心となる課題**：この種のクエリは、定量化可能な構造化条件（スキル、年数）と、スキーマを事前定義できない定性的条件（「プロジェクトを独立して担当した経験」のような、読解でしか判断できない表現）が混ざっており、単純なベクトル類似度検索では**網羅性・完全性を保証できない**——top-k検索では、表現は異なるが条件に合致する候補者を見逃す可能性がある。

**採用予定の設計**（未検証、今後実測データを補足すべき）：
1. インデックス段階：LLMで各履歴書を構造化フィールド（スキル一覧、プロジェクトの日付から逆算した年数）に抽出し、原文のembeddingだけでなくChromaのmetadataとして保存する
2. クエリ段階ではまず「クエリ理解」を行う：自然言語の質問を構造化条件に解析する
3. 構造化条件でまずmetadataフィルタをかけ候補を絞り込み、定性条件については残った候補者ひとりひとりに対してLLMで再確認を行い、**原文の根拠を引用させる**——「はい／いいえ」だけを出力させない

設計方針として記録しておき、実際に実装した後に実測結果（本当に「見逃し」問題を解決できたか、LLM呼び出しコストがどれだけ増えるか）を追記すべきで、[parameter-tuning.ja.md](parameter-tuning.ja.md) のような評価ドキュメントを別途作成すべき。

## 三、まだ決まっていない設計上の課題

- **D7の適応的チャンキング方式**：現時点では「未実施」と判断しているが、今後履歴書以外のフォーマットの文書を扱う必要が出てきたら、この判断は再評価が必要。
- **D12の履歴書スクリーニング構成**：現時点では議論稿にすぎず、具体的なmetadataスキーマ、クエリ解析のプロンプト設計、LLM再確認のコスト／遅延が許容範囲かどうか、いずれも実測データの裏付けがない。
- **D4の「速度 vs 精度」のトレードオフ**：現在選んでいるのは「約85%の精度を受け入れて数十倍の速度を得る」という判断だが、これは一度きりの判断であり、より強力なモデルへの切り替えや、失敗パターン（「複数情報ポイント」のシナリオなど）への個別対応による再評価は行っていない。
