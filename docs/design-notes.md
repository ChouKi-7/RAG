## 一、整体架构

一句话：对着PDF做"开卷问答"——先把文档切片、转成向量存起来；用户提问时，先检索出语义最相关的几个片段，再把这些片段和问题一起交给大模型，让它基于真实原文回答，而不是凭空编。

```
PDF → 切块(chunk) → 向量化(embedding) → 存入向量库(Chroma)
                                              │
用户提问 → 向量化 → 相似度检索(取最相关的k段) → 相关度过滤 → 拼进prompt → LLM生成回答
```

两个核心文件：`rag_pipeline.py`（RAG的5个步骤）、`main.py`/`app.py`（分别是CLI外壳和Web外壳，调用同一套pipeline）。

## 二、设计决策时间线

按大致做出决策的时间顺序排列，不是按模块分类——这样能看出"为什么在那个时间点做了那个选择"。

### D1（2026-10-01）embedding模型要选多语言的，不能只看"默认/最流行"

最初用的是 `all-MiniLM-L6-v2`，英语为主训练，日语文档检索直接失效（问"他叫什么"答"不知道"，但原文第一句就写着姓名）。换成 `paraphrase-multilingual-MiniLM-L12-v2` 后才正常。

**教训**：embedding模型必须跟文档实际语言匹配，用错了**不会报错，只会悄悄检索失效**——这种坑不主动测试很难发现。详见 [bug-log.md #4](bug-log.md)。

### D2（2026-10-01）向量库要做"存在就加载，不存在才新建"的判断

最初 `build_vector_store()` 每次运行都无条件重新计算全部embedding、重写向量库。改成先检查 `persist_directory` 是否已存在且非空，有就直接加载——省去重复计算的开销。详见 [project-notes.md 四-5](project-notes.md)。

这个决策后来间接导致了 D7 那个隐私bug（见下），因为"复用已有连接/collection"和"每次会话要互相隔离"其实是两个互相拉扯的需求，当时只想到了前者。

### D3（2026-10-01）回答生成模型：Claude → Gemini（免费额度优先于"原本设计"）

项目最初设计是用Claude（`ChatAnthropic`）做回答生成，但申请key需要先充值。为了能继续免费学习/测试，切换成Google Gemini。**Claude相关代码没删，只是注释保留**，想切回去随时可以——这是刻意的决定，不是简单图省事，因为供应商之间原理完全一样（都是"调用云端大模型做理解+生成"），切换成本应该保持很低。详见 [project-notes.md 三](project-notes.md)。

同时也调研过Groq、Ollama（纯本地）、Hugging Face Inference API等其他免费/低成本方案，记录在案但没有切换需求，暂不实施。

### D4（2026-10-26）模型选型是一个"速度 vs 准确率"的量化权衡，不是拍脑袋换的

`gemini-3.8-flash` 免费额度只有20次/天，而且响应速度会随着接近额度上限逐渐变慢（150~367秒）。换成 `gemini-3.1-flash-lite` 后速度快了几十倍（平均4.76秒），但代价是**准确率从未知基线掉到了实测约85%**——用13题+跨文档6题的评测验证过，失败模式集中在"同一段里有多个信息点，模型偶尔漏抓其中一个"。

这是目前项目里唯一一个**经过量化实验、公开承认有取舍**的设计决策，而不是"换了觉得更好"。详见 [project-notes.md 四-15](project-notes.md)。

### D5（2026-10-26）相关度过滤：按embedding provider分别设阈值，而不是写死一个数字

为了防止模型在"文档里根本没有答案"的情况下瞎编，加了相关度分数过滤：检索到的片段如果分数未达标，直接返回"未找到相关内容"，不调用LLM。

实测发现：同样是"相关"的内容，本地HuggingFace embedding给出的分数量级（16~18）和云端Google embedding给出的分数量级（0.69~0.76）完全不是一个尺度（而且本地模型分数越高越不相关、云端模型分数越低越相关，两者连"方向"都相反）。所以阈值做成了按provider查表的字典，而不是全局一个常量，同时留了环境变量兜底覆盖。详见 [project-notes.md 四-10](project-notes.md)。

### D6（2026-10-26）向量库必须按"会话"隔离，默认collection_name是不安全的

`Chroma.from_documents()` 不指定 `collection_name` 时默认值固定是 `'langchain'`。`persist_directory=None` 的内存模式下，同一进程内连续调用（Web版每次有用户上传新PDF都会调用一次）会不断往同一个collection里追加数据，不清空重建——**不同用户上传的文档内容会在向量库里串台，是一个真实的隐私泄露风险**，不只是功能bug。

修复方式是每次调用传 `collection_name=f"session-{uuid.uuid4()}"`，强制每次都是独立的向量空间。这个决策的教训是：D2里"复用已有向量库"的优化思路，必须明确区分"同一份文档重复处理可以复用"和"不同会话/不同文档必须互相隔离"这两种场景，不能用同一套默认行为应付。详见 [bug-log.md #8](bug-log.md)。

### D7（2026-10-26）chunk_size不是拍脑袋设的默认值，是实测调出来的

默认 `chunk_size=500` 不是最优值。做了"同一文档换参数"和"同一参数换文档"两组对比实验（过程中还顺带挖出了D6那个隐私bug，第一轮数据因此作废重跑），最终把默认值改成 `800`，测试中拿到满分。完整实验设计、数据、局限性讨论见 [parameter-tuning.md](parameter-tuning.md)，这里不重复。

**尚未实施的后续研究**（记录为课题，不是待办）：固定按字符数切块，对短文档/特定格式文档不是最优解，讨论过"自定义切割优先级""按项目分段""语义分块""短文档不切"四种自适应方案，权衡后判断"按当前格式特化的简单规则"性价比最高，语义分块是"杀鸡用牛刀"，暂不实施。详见 [project-notes.md 四-17](project-notes.md)。

### D8（2026-10-26）测试策略：只测不碰网络的纯逻辑，真实LLM调用刻意不自动化测试

单元测试覆盖 `split_into_chunks()`、`_build_prompt()`、阈值表、"未找到"提示文案这类确定性逻辑，**刻意不**覆盖 `ask_question()`/`build_qa_chain()` 这些要真实调用Gemini API的函数——理由很明确：没有可以安全暴露在CI里的key、调用结果不确定性强、会消耗免费额度。这是"测什么/不测什么"的边界划分，不是偷懒漏测，原因写在 [test-cases/unit-test-cases.md](../test-cases/unit-test-cases.md) 里。

### D9（2026-10-27）CI/CD：测试是部署的前置门禁，镜像必须用唯一tag不能用`:latest`

两个独立但相关的设计决定：
1. `test` job（lint+单元测试）跑不过，`build-and-deploy` job 不会触发——质量门禁和部署自动化必须是同一条流水线，不能分开。
2. 镜像tag不能只用 `:latest`：Azure Container Apps判断"要不要拉新镜像"，依据的是**镜像地址字符串本身有没有变**，不检查标签背后内容变没变。固定tag会导致"GitHub Actions全程显示绿色成功，但Azure其实一直在跑最早那次部署的老镜像"——这是个非常隐蔽的"假成功"陷阱，真实发生过（见 [bug-log.md #10](bug-log.md)）。修复方案是额外打一个"日期+commit短哈希"的唯一tag用于实际部署。

### D10（2026-10-26）日志分级：内部状态用logger，用户界面文字保留print

`rag_pipeline.py` 里描述内部处理步骤的输出，从 `print` 换成 `logger.info`/`logger.warning`；但 `main.py` 里真正面向CLI用户的交互文字（提问、报错提示）**刻意保留print**，不算进这次改动范围——因为那是用户界面，不是内部状态日志，两者职责不同不该用同一套机制。详见 [project-notes.md 四-14](project-notes.md)。

### D11（2026-10-26）访问控制做成可选特性，不强制所有部署都要配置

Web Demo的密码门禁通过可选环境变量 `APP_PASSWORD` 实现：设置了才启用校验，不设置完全不受影响、本地开发照常直接用。这样本地开发体验和"给外人看之前要加一道门"这个需求不冲突，不用维护两套代码路径。详见 [project-notes.md 四-9](project-notes.md)。

### D12（2026-11-02，已实现，v2）简历多人筛选功能：结构化过滤 + 定性复核的混合架构，刻意不用向量检索

这是项目的v2方向：把单文档语义问答，扩展成"对多份简历做条件筛选"（比如"找一个Python 3年以上、能独立负责项目的人"）。详细实现见 [resume-screening-notes.md](resume-screening-notes.md)，这里只记录架构上的"为什么"。

**核心问题**：这类查询混合了可量化的结构化条件（技能、年限）和没法预定义schema的定性条件（"独立负责项目的经验"这种只能靠阅读理解判断的说法），而单纯的向量相似度检索**做不到穷举/完整性保证**——top-k检索可能漏掉表述不同但符合条件的候选人。

**实际采用的架构**（`resume_screening.py`，跟v1的`rag_pipeline.py`是两条独立的流程，不复用Chroma）：
1. **索引阶段**：用LLM把每份简历整篇（不切块）抽取成结构化字段——技能列表+按项目日期推算的年限、是否有独立负责项目的经验+原文依据。用`pydantic.BaseModel` + `with_structured_output()`强制输出格式，不是手写prompt让LLM"尽量"输出JSON
2. **查询理解**：把用户的自然语言问题也用同一套机制解析成结构化条件（技能、最低年限、定性要求）
3. **两段式筛选**：先用解析出的技能/年限对结构化字段做**纯Python逻辑过滤**（`filter_by_structured_criteria()`，不调用LLM，保证不会漏判、可以单元测试），缩小候选范围后，再对剩下的候选人逐个针对定性要求跑LLM复核，**要求输出原文引用**而不是只给是/否

**刻意没有用Chroma/向量检索**，这是和v1最大的架构差异：v1的"检索相关片段"模式天生适合"回答一个开放问题"，但不适合"保证筛出所有符合条件的人"——把简历切成chunk反而会把"这个人Java用了几年"这种需要整篇上下文才能算出来的信息打散。所以v2的"索引"根本不经过向量库，就是一份JSON结构化记录的列表，筛选靠结构化字段精确匹配，复核靠整篇原文喂给LLM判断，两步都不依赖相似度检索。

**抽取结果会缓存**（`resume_profiles_cache.json`，按文件内容哈希失效），复用了D2"已有就不重算"的思路——结构化抽取同样要调用LLM，没必要每次启动都重新跑一遍。

### D13（2026-11-02）结构化输出(`with_structured_output`)不能假设一定成功，必须有文本兜底解析

实测时发现：`gemini-3.1-flash-lite`对短文档能正常通过"函数调用(tool call)"机制返回结构化结果，但喂给它信息量更大的长文档（职务经历完整的那份真实简历）时，模型有时会放弃函数调用，直接把JSON包在普通文本回答的` ```json `代码块里——这种情况下`with_structured_output()`拿不到可解析的tool call，**不报错，直接返回`None`**，调用方如果没防这一手会直接崩溃。详见 [bug-log.md #12](bug-log.md)。

**采用的方案**：写了`_invoke_structured()`包装函数，`include_raw=True`拿到原始响应，`parsed is None`时用正则从文本里抠出JSON再手动校验，而不是假设"调用结构化输出就一定拿到结构化结果"。这个教训对所有用`with_structured_output()`的地方都适用，不只是这个功能——以后新加其他结构化抽取逻辑时应该直接复用这个包装函数，而不是重新手写一遍`try/except`。

### D14（2026-11-10）技能名匹配：子串匹配换成单词边界匹配，但要单独处理符号开头/结尾的技能名

D12上线时就知道`filter_by_structured_criteria()`用的是"大小写不敏感的子串匹配"会有"Java误中JavaScript"这种问题，当时记在"还没定的设计问题"里没有立刻修——直到专门设计了一批含"只有JavaScript、完全没有Java"这种候选人的测试简历，才第一次**实测复现**出来（[bug-log.md #14](bug-log.md)）。这个顺序本身就是个教训：写进文档的"已知局限"，如果没有针对性的测试数据，会一直停留在"理论上如此"，不会主动被验证。

**采用的方案**：用`\b`（单词边界）把查询词包起来再匹配，让"java"不再能作为"javascript"内部的子串被匹配上，但仍然允许"Spring"匹配"Spring Boot"这种"整词出现在更长字符串里"的情况。

**修复过程中差点引入的新bug**：`\b`只在"英数字字符"和"非英数字字符"的切换处生效，如果查询词本身以符号开头/结尾（比如`C#`、`.NET`），直接套用`\bC#\b`这种写法会导致**连它自己都匹配不上**（`#`是非英数字，字符串末尾也被当成非英数字，两边都是非英数字就不存在"边界"）。最后的实现是：只在查询词的首/尾字符是英数字时才加边界条件，符号开头/结尾的技能名不加。这个边界情况是写单元测试时才发现的，不是一开始就想到的——提醒了一点：**修一个边界case的bug时，修复方案本身也该补边界case的测试**，不能只验证原始bug场景。

**还没解决的部分**：同义词/别名（"機械学習"vs"ML"、"Golang"vs"Go"）完全没处理，这不是这次修复的范围，留在"还没定的设计问题"里。

### D15（2026-11-17，已修复年限低估，发现并保留了一个新问题）准确率评测发现：确定性过滤逻辑再正确，也救不了上游给错的数字

做[系统性准确率评测](resume-screening-eval.md)时发现：`extract_candidate_profile()`推算的技能年限，有3位候选人明显偏低（详见[bug-log.md #15](bug-log.md)）。深挖后定位到真正根因——**不是"表述简略"，是LLM不知道"今天"是哪一天**。这几位候选人的共同点是最新/唯一的工作经历都写"〜現在"这种开放区间，LLM缺一个确定的终点去计算跨度。而算得准的几位，其实不是LLM自己算的，是摘要里直接写了总数，被原样抄过去而已。

这次发现之所以值得单独记一条设计笔记，是因为它暴露了D12架构里一个没有明说的假设：**"确定性过滤保证不会漏判"这句话，成立的前提是喂给过滤器的结构化数据本身是准的**。`filter_by_structured_criteria()`的比较逻辑（`0.5 < 1`时排除）完全正确，排除的决定本身没有任何问题——问题出在它比较的那个"0.5"从一开始就算错了。换句话说，D12设计里"把贵的LLM操作和便宜的确定性操作分开"这个思路没有错，但**"确定性"只能保证"过滤这一步"不出错，不能保证"过滤的输入"是对的**，这是两件独立的事，之前没有把这个边界讲清楚。

**采用的修复**：在抽取prompt里显式告诉LLM今天的日期（`datetime.date.today()`），让"現在"有一个确定的计算终点。验证下来，3位候选人的年限从0.5/0.75/0.5正确修正到1.6/2.6/1.6，之前8条测试查询里漏判的那一条变成完全吻合。

### D16（2026-11-17）修prompt不能"改一句、跑一次、看效果"，这样调试出来的"修好了"可能只是噪音

修D15那个年限偏低问题时，先后试了两版prompt：第一版只加"今天日期"，第二版在第一版基础上又加了一句"归属约束"（要求只有项目业务内容/使用技术里明确提到某技能，才能把那段时间算进该技能的年限）。

**结果**：第二版不但没解决"松本さくら的Java年限被错误地算进了她现在这份跟Java无关的PM工作时长"这个问题，反而让这个数字从13.6涨到了15.0（更错），还连带把其他候选人本来正确的技能条目搅乱了（比如凭空多出两条不存在的技能、原本正确的数字变成别的数字）。

**这次教训的核心**：结构化输出是LLM一次性生成一整个JSON对象，**改prompt里的一句话，影响的不是"局部"，是整个生成过程**——即使那句话只针对某个字段，模型对整段指令的"理解"变了，连带着看起来完全不相关的字段也可能跟着变。这意味着"改一句话→跑一次→看这次结果是不是比上次好"这种调试方式，得到的"变好了"或"变差了"都可能只是一次性的噪音，不是真正验证过的因果关系——要严谨验证，得对同一个prompt多跑几次看稳定性，而不是跑一次就下结论。

**最终处理方式**：没有继续加prompt去"赌"能修好，而是做了减法——撤销第二版那句"归属约束"（因为撤掉之后再测试，问题数字还是13.6，证明那句约束本身不是这个问题的根源，加不加都一样），只保留第一版"告知日期"这个经过验证确实有效的改动。松本さくら这个案例作为已知问题照实记录（详见[bug-log.md #16](bug-log.md)），不继续硬修。

### D17（2026-11-18）技能名同义词：选了embedding相似度兜底，不是LLM判断，也不是同义词表——先用真实数据测过阈值能不能成立，再决定要不要做

技能名匹配修到D14之后，还剩一个不同类型的问题：同义词（"ML"vs"機械学習"、"Go"vs"Golang"），这种不是"同一个词的变体"，是"两个完全不同的字符串表示同一个意思"，单词边界匹配这种字符串比对方法天生碰不到。

**考虑过三个方向**：
1. 维护一个人工同义词表——简单、免费、确定性，但只能覆盖提前想到的词，没录入的新词还是认不出来
2. 查询时让LLM判断"这两个技能是不是一回事"——覆盖面最广，但会把D12里"过滤这一步必须是免费、快、确定性"的设计原则破坏掉，变成每次过滤都要调LLM
3. 用embedding算语义相似度，超过阈值就算匹配——比LLM判断便宜（本地模型不花钱），比同义词表通用，但多了"阈值怎么定"这个新问题，而且把"确定性过滤"变成了"模糊匹配"

**先验证可行性，再决定要不要做**：选方向3之前，没有直接动手实现，而是先用项目里已有的本地embedding模型（`rag_pipeline.get_embeddings()`，本来是给v1的向量检索用的）跑了一组真实数据测试，算了几对"应该匹配"和"不该匹配"的词的余弦相似度。结果暴露了一个关键矛盾：`"ML"`vs`"機械学習"`只有0.334分，但`"Java"`vs`"JavaScript"`（就是D14修的那个问题）有0.441分——**比真同义词的分数还高**。这意味着任何一个阈值，要么漏掉"ML/機械学習"这类真同义词，要么让bug#14复活，没有两全的数字。

**最终采用的方案**：阈值定在0.5，这样"Go/Golang"（0.766）、"JS/JavaScript"（0.770）这类分数够高的同义词能拾到，"Java/JavaScript"（0.441）这类危险对照组排除在外（bug#14不会复活），代价是"ML/機械学習""AWS/Amazon Web Services"这类字面差异太大的缩写拾不到。这是一个**主动接受局限、不是假装解决了**的决定——不是"这个方案完美"，是"这个方案比什么都不做好，而且不会制造新问题"。

**实现细节**：embedding计算是"按需触发"的兜底——`_skill_matches()`先走原有的单词边界匹配，只有没匹配上才会去算向量，已经能匹配上的不会多余地调用embedding模型（省计算）。`filter_by_structured_criteria()`、`screen_candidates()`等函数都加了`embeddings`参数透传下去，不传（`None`）的话行为跟D14修完之后完全一样，不影响没升级调用方式的旧代码。

**还没解决的部分**：缩写/别名这类字面差异极大的同义词依然抓不住，留在"还没定的设计问题"里，不是这次的目标。

### D18（2026-11-24）结果排序：有定性条件时按LLM打分排，没有的话按年限排——不浪费已经付出的成本去额外排序

v2上线以来，筛选结果一直是无序列表，这在"帮我找2个Java经验的人"这种带数量限制的问题上完全没法回答——无序列表里随便截取前2个毫无意义。

**排序依据，按有没有定性条件分两种**：
- **有定性条件**（比如"能独立负责项目"）：`judge_qualitative()`本来就要对每个候选人单独调一次LLM，这次顺手让它多输出一个`match_score`（0-100），排序直接用这个分数，不需要额外成本
- **没有定性条件**（纯技能+年限的查询，比如"Java 5年以上"）：这一步完全没有调用过LLM，候选人本身也没有可比较的"匹配度"，所以直接复用已经抽取好的技能年限数字来排序，同样不产生额外成本

这个设计延续了D12"贵的操作用在刀刃上、能用已有数据就不额外花钱"的思路——排序功能本身**没有新增一次LLM调用**，纯粹是复用已经算出来的数字（`match_score`或者`years`）。

**`limit`参数**：`parse_query()`顺手把"两个人""上位3件"这类数量要求也解析出来，排序完成后再截断。实现上是先排序、再截断，不是反过来，保证"前N个"真的是"最匹配的N个"，不是"随便N个"。

**实测发现的一个现象（不是bug，但值得记录）**：定性判断的打分是**逐个候选人独立做的**，不是一次性把所有人放一起比较排名，所以当多个人"明显都很符合"时，经常会打出并列的分数（比如实测9个候选人里，排名前3的都给了100分）。并列分数之间的先后顺序取决于`sorted()`的稳定排序特性，实质上是"候选人列表原本的顺序"，不代表"並列的人里谁更好"——这是"独立打分"这个设计天然的局限，如果想要真正的"total ranking"（而不是"分层排名+组内随意顺序"），需要让LLM一次性看到所有候选人做比较式排序，但那样做不仅会把"过滤这一步保持确定性/低成本"的设计推翻，还会把一次查询的LLM调用量从"候选人数"级别推高到更复杂的量级，目前判断不值得为了解决"并列名次内部排序"这么小的问题去交换这个代价。

**后续专项验证（2026-11-24）**：担心"并列100分"是不是因为打分机制本身区分度不够、敷衍了事，专门做了一次`match_score`的弁别性+安定性测试（用强弱程度无争议的合成文本，而不是真实候选人互相比较，详见[resume-screening-eval.md 七](resume-screening-eval.md)）。结果显示打分机制本身是可信的：4段强度递减的文本，分数也跟着递减（100→30→10→0），而且同一输入重复3次结果完全一致。这说明"并列100分"更可能是因为那几位候选人的证据强度本来就接近同一档次，不是打分机制失效——**上面说的"组内顺序无意义"这个局限依然成立（因为没有比较式排序），但至少确认了"打分这件事本身没有偷懒"**。

- **D4那个"速度vs准确率"的权衡**：目前选的是"接受约85%准确率换几十倍速度"，但这是个一次性判断，没有重新评估过是否要换更强的模型、或者针对失败模式做针对性修复（比如对"多信息点"场景做二次确认）。
- **D16遗留的技能-项目归属问题**：松本さくら的Java年限被错误计入了无关项目的时长，目前已知但未修复，暂不继续用"猜prompt"的方式处理，留给以后有更可靠验证手段（比如多次重跑取稳定结果）时再碰。
- **D17的embedding阈值是不是最优**：0.5这个数字只是"不会让bug#14复发"的下限附近挑的，没有系统性网格搜索过更多数据点，候选人/技能种类变多后可能需要重新校准；另外本地embedding模型本身的选型也没对比过其他模型会不会在这组数据上表现更好。
- **D12评测里"10份量级下的成本/延迟"**：之前#13的限流问题证明了"候选人一多+无结构化条件"会撞限流，但具体延迟/调用次数的量化数据还没系统整理过。
- **D18的并列分数排序问题**：定性判断逐个候选人独立打分，明显符合的候选人经常并列最高分，组内顺序目前靠`sorted()`的稳定性（即候选人列表原始顺序），不代表真实的相对优劣。要不要为了解决这个问题引入"比较式排序"（一次性把候选人放一起比较），目前判断代价（破坏确定性过滤+推高LLM调用量）大于收益，暂不处理。
