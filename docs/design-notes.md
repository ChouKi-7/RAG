## 一、整体架构

一句话：对着PDF做"开卷问答"——先把文档切片、转成向量存起来；用户提问时，先检索出语义最相关的几个片段，再把这些片段和问题一起交给大模型，让它基于真实原文回答，而不是凭空编。

```
PDF → 切块(chunk) → 向量化(embedding) → 存入向量库(Chroma)
                                              │
用户提问 → 向量化 → 相似度检索(取最相关的k段) → 相关度过滤 → 拼进prompt → LLM生成回答
```

两个核心文件：`rag_pipeline.py`（RAG的5个步骤）、`main.py`/`app.py`（分别是CLI外壳和Web外壳，调用同一套pipeline）。

## 二、设计决策时间线

按大致做出决策的时间顺序排列，不是按模块分类——这样能看出"为什么在那个时间点做了那个选择"。

### D1（2026-10-01）embedding模型要选多语言的，不能只看"默认/最流行"

最初用的是 `all-MiniLM-L6-v2`，英语为主训练，日语文档检索直接失效（问"他叫什么"答"不知道"，但原文第一句就写着姓名）。换成 `paraphrase-multilingual-MiniLM-L12-v2` 后才正常。

**教训**：embedding模型必须跟文档实际语言匹配，用错了**不会报错，只会悄悄检索失效**——这种坑不主动测试很难发现。详见 [bug-log.md #4](bug-log.md)。

### D2（2026-10-01）向量库要做"存在就加载，不存在才新建"的判断

最初 `build_vector_store()` 每次运行都无条件重新计算全部embedding、重写向量库。改成先检查 `persist_directory` 是否已存在且非空，有就直接加载——省去重复计算的开销。详见 [project-notes.md 四-5](project-notes.md)。

这个决策后来间接导致了 D7 那个隐私bug（见下），因为"复用已有连接/collection"和"每次会话要互相隔离"其实是两个互相拉扯的需求，当时只想到了前者。

### D3（2026-10-01）回答生成模型：Claude → Gemini（免费额度优先于"原本设计"）

项目最初设计是用Claude（`ChatAnthropic`）做回答生成，但申请key需要先充值。为了能继续免费学习/测试，切换成Google Gemini。**Claude相关代码没删，只是注释保留**，想切回去随时可以——这是刻意的决定，不是简单图省事，因为供应商之间原理完全一样（都是"调用云端大模型做理解+生成"），切换成本应该保持很低。详见 [project-notes.md 三](project-notes.md)。

同时也调研过Groq、Ollama（纯本地）、Hugging Face Inference API等其他免费/低成本方案，记录在案但没有切换需求，暂不实施。

### D4（2026-10-26）模型选型是一个"速度 vs 准确率"的量化权衡，不是拍脑袋换的

`gemini-3.8-flash` 免费额度只有20次/天，而且响应速度会随着接近额度上限逐渐变慢（150~367秒）。换成 `gemini-3.1-flash-lite` 后速度快了几十倍（平均4.76秒），但代价是**准确率从未知基线掉到了实测约85%**——用13题+跨文档6题的评测验证过，失败模式集中在"同一段里有多个信息点，模型偶尔漏抓其中一个"。

这是目前项目里唯一一个**经过量化实验、公开承认有取舍**的设计决策，而不是"换了觉得更好"。详见 [project-notes.md 四-15](project-notes.md)。

### D5（2026-10-26）相关度过滤：按embedding provider分别设阈值，而不是写死一个数字

为了防止模型在"文档里根本没有答案"的情况下瞎编，加了相关度分数过滤：检索到的片段如果分数未达标，直接返回"未找到相关内容"，不调用LLM。

实测发现：同样是"相关"的内容，本地HuggingFace embedding给出的分数量级（16~18）和云端Google embedding给出的分数量级（0.69~0.76）完全不是一个尺度（而且本地模型分数越高越不相关、云端模型分数越低越相关，两者连"方向"都相反）。所以阈值做成了按provider查表的字典，而不是全局一个常量，同时留了环境变量兜底覆盖。详见 [project-notes.md 四-10](project-notes.md)。

### D6（2026-10-26）向量库必须按"会话"隔离，默认collection_name是不安全的

`Chroma.from_documents()` 不指定 `collection_name` 时默认值固定是 `'langchain'`。`persist_directory=None` 的内存模式下，同一进程内连续调用（Web版每次有用户上传新PDF都会调用一次）会不断往同一个collection里追加数据，不清空重建——**不同用户上传的文档内容会在向量库里串台，是一个真实的隐私泄露风险**，不只是功能bug。

修复方式是每次调用传 `collection_name=f"session-{uuid.uuid4()}"`，强制每次都是独立的向量空间。这个决策的教训是：D2里"复用已有向量库"的优化思路，必须明确区分"同一份文档重复处理可以复用"和"不同会话/不同文档必须互相隔离"这两种场景，不能用同一套默认行为应付。详见 [bug-log.md #8](bug-log.md)。

### D7（2026-10-26）chunk_size不是拍脑袋设的默认值，是实测调出来的

默认 `chunk_size=500` 不是最优值。做了"同一文档换参数"和"同一参数换文档"两组对比实验（过程中还顺带挖出了D6那个隐私bug，第一轮数据因此作废重跑），最终把默认值改成 `800`，测试中拿到满分。完整实验设计、数据、局限性讨论见 [parameter-tuning.md](parameter-tuning.md)，这里不重复。

**尚未实施的后续研究**（记录为课题，不是待办）：固定按字符数切块，对短文档/特定格式文档不是最优解，讨论过"自定义切割优先级""按项目分段""语义分块""短文档不切"四种自适应方案，权衡后判断"按当前格式特化的简单规则"性价比最高，语义分块是"杀鸡用牛刀"，暂不实施。详见 [project-notes.md 四-17](project-notes.md)。

### D8（2026-10-26）测试策略：只测不碰网络的纯逻辑，真实LLM调用刻意不自动化测试

单元测试覆盖 `split_into_chunks()`、`_build_prompt()`、阈值表、"未找到"提示文案这类确定性逻辑，**刻意不**覆盖 `ask_question()`/`build_qa_chain()` 这些要真实调用Gemini API的函数——理由很明确：没有可以安全暴露在CI里的key、调用结果不确定性强、会消耗免费额度。这是"测什么/不测什么"的边界划分，不是偷懒漏测，原因写在 [test-cases/unit-test-cases.md](../test-cases/unit-test-cases.md) 里。

### D9（2026-10-27）CI/CD：测试是部署的前置门禁，镜像必须用唯一tag不能用`:latest`

两个独立但相关的设计决定：
1. `test` job（lint+单元测试）跑不过，`build-and-deploy` job 不会触发——质量门禁和部署自动化必须是同一条流水线，不能分开。
2. 镜像tag不能只用 `:latest`：Azure Container Apps判断"要不要拉新镜像"，依据的是**镜像地址字符串本身有没有变**，不检查标签背后内容变没变。固定tag会导致"GitHub Actions全程显示绿色成功，但Azure其实一直在跑最早那次部署的老镜像"——这是个非常隐蔽的"假成功"陷阱，真实发生过（见 [bug-log.md #10](bug-log.md)）。修复方案是额外打一个"日期+commit短哈希"的唯一tag用于实际部署。

### D10（2026-10-26）日志分级：内部状态用logger，用户界面文字保留print

`rag_pipeline.py` 里描述内部处理步骤的输出，从 `print` 换成 `logger.info`/`logger.warning`；但 `main.py` 里真正面向CLI用户的交互文字（提问、报错提示）**刻意保留print**，不算进这次改动范围——因为那是用户界面，不是内部状态日志，两者职责不同不该用同一套机制。详见 [project-notes.md 四-14](project-notes.md)。

### D11（2026-10-26）访问控制做成可选特性，不强制所有部署都要配置

Web Demo的密码门禁通过可选环境变量 `APP_PASSWORD` 实现：设置了才启用校验，不设置完全不受影响、本地开发照常直接用。这样本地开发体验和"给外人看之前要加一道门"这个需求不冲突，不用维护两套代码路径。详见 [project-notes.md 四-9](project-notes.md)。

### D12（规划中，尚未实施）简历多人筛选功能：结构化过滤 + 语义复核的混合架构

这是目前还在讨论阶段、还没写代码的新方向：把项目从"对单份文档的语义问答"，扩展成"对多份简历做条件筛选"（比如"找一个学Java 5年、能独立负责项目的人"）。

**核心问题**：这类查询混合了可量化的结构化条件（技能、年限）和没法预定义schema的定性条件（"独立负责项目的经验"这种只能靠阅读理解判断的说法），而单纯的向量相似度检索**做不到穷举/完整性保证**——top-k检索可能漏掉表述不同但符合条件的候选人。

**打算采用的设计**（尚未验证，后续应该补充实测数据）：
1. 索引阶段：用LLM把每份简历抽取成结构化字段（技能列表、按项目日期推算的年限），存成Chroma的metadata，而不是只存原文embedding
2. 查询阶段先做"查询理解"：把自然语言问题解析成结构化条件
3. 结构化条件先用metadata过滤缩小候选范围，定性条件再对剩下的候选人做逐份LLM复核，并要求**引用原文依据**，不是只输出是/否

记录为设计方向，等真正实现后把实测结果（是否真的解决了"漏判"问题、额外的LLM调用成本有多大）补充进来，并且应该单独开一份类似 `parameter-tuning.md` 的评测文档。
