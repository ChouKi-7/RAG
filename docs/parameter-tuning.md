# 第一部分：chunk_size / chunk_overlap

> 目的：验证 `split_into_chunks()` 的 `chunk_size`/`chunk_overlap` 默认值（500/50）是不是对这类文档（结构化的职务経歴書）合适的参数，顺便验证模型在不同文档上的准确率是否稳定。

## 一、实验设计

### 深度测试（同一文档，换参数）
用 userA 的简历（4页，内容最丰富），固定一批 **15 道题**（12道有明确答案的相关问题 + 3道故意不相关的问题），在三组 `chunk_size`/`chunk_overlap` 参数下分别重新建向量库、重新跑一遍完整提问：

- `300/30`（偏小）
- `500/50`（当前代码默认值，基线）
- `800/80`（偏大）

同一批题目在三组参数间完全复用，只变参数这一个变量，排除"题目难度不同"这个干扰因素。

### 广度测试（同一参数，换文档）
固定用默认的 `500/50`，换4份不同的简历（userA + 另外生成的3份虚构测试简历：厨师/护士/广告营业，分别代表不同行业、不同篇幅），各问4道题（userA 的数据直接复用深度测试里 `500/50` 那组的结果，不重复跑）。

### 技术细节
- Embedding: `EMBEDDING_PROVIDER=google`（跟 Azure 云端部署配置一致）
- LLM: `gemini-3.1-flash-lite`（当前代码默认模型）
- 向量库: `persist_directory=None`（内存模式，跟 Web 版 `app.py` 一致）
- `temperature=0`，理论上同样的输入应该每次得到同样的输出

---

## 二、⚠️ 第一次跑的数据作废，发现了一个严重 bug

第一次评测时，三组 `chunk_size` 的正确率**完全一样**（都是 86.7%），广度测试的几份简历准确率却低得离谱（25%、50%、25%），其中还出现"问厨师简历的资格，却回答了 userA 的资格"这种明显串台的情况。

排查后发现：**`build_vector_store(persist_directory=None)` 在同一个 Python 进程里连续调用多次时，不同文档的向量库数据会累积在一起，不是真正独立的**（根因是 `Chroma.from_documents()` 默认的 `collection_name` 是固定值 `'langchain'`，没有手动指定的话同进程内的调用全部写进同一个集合）。这不只是这次评测脚本的问题——**`app.py`（Web版）用的就是这个代码路径，意味着线上部署如果进程不重启，不同用户上传的PDF内容可能会互相"串台"，是一个真实的正确性+隐私风险**。

已经修复（给每次调用传一个 `uuid.uuid4()` 生成的唯一 `collection_name`），详细记录见 [docs/project-notes.md](project-notes.md) 第16条。下面的数据，都是修复之后重新跑的，干净可信。

---

## 三、深度测试结果（userA简历，15题，3组参数）

| chunk_size/overlap | chunk数 | 正确率 | 平均耗时 | 答错的题 |
|---|---|---|---|---|
| 300/30 | 33 | 13/15（86.7%） | 12.63s | 姓名、Jetson项目时间 |
| 500/50 | 16 | 14/15（93.3%） | 10.28s | 家畜保険系统用的语言 |
| **800/80** | **12** | **15/15（100%）** | 28.21s | 无 |

**结论：chunk_size 越大，这份文档上的准确率越高，呈现清晰的单调趋势。** 这跟之前排查"家畜保険"那次发现的根因一致——chunk 切得小，容易把"项目名"和"项目细节/技术栈"拆散到不同块，模型拼不出完整信息；chunk 越大，一个完整的项目段落越不容易被切散。

**耗时没有跟 chunk_size 呈现干净的关系**（800组反而平均最慢，但这组里有单题 87秒、70秒、209秒这种极端值拉高了平均数）——大概率还是被之前排查过的那个"gRPC偶发连接不稳定"老问题主导，不是 `chunk_size` 本身导致变慢。

## 四、广度测试结果（固定500/50，4份简历）

| 简历 | chunk数 | 正确率 | 平均耗时 |
|---|---|---|---|
| userA（基线复用） | 16 | 14/15（93.3%） | 10.28s |
| 田中健一（厨师） | 2 | 4/4（100%） | 11.31s |
| 鈴木美咲（护士） | 2 | 3/4（75%） | 3.92s |
| 高橋大輔（广告营业） | 2 | 4/4（100%） | 37.62s |

整体正确率：25/27 ≈ **92.6%**。

唯一的失误（护士那份，"インシデント報告件数は前年比何パーセント削減しましたか"）是**检索层直接拦截**（相关度分数 0.826/0.831，刚好卡在 0.8 阈值上方一点点），不是模型读错——这份文档只切出2个chunk，内容很短，阈值 `0.8` 对这种超短文档可能偏严了一点，导致本该通过的内容被挡在外面。

---

## 五、结论与建议

1. **`chunk_size` 对这类结构化简历文档确实有实际影响**，默认值 `500/50` 不是最优的，**`800/80` 在这次测试中拿到满分**。建议考虑把默认值调大。
2. **换不同文档测试，准确率整体保持在 90% 左右**，说明当前这套 pipeline（embedding + 阈值过滤 + `gemini-3.1-flash-lite`）在"结构化简历类文档"这个场景下，具备基本的跨文档稳定性，不是只对 userA 那份简历调优过的特例。
3. **相关度阈值 `0.8`（google provider）对超短文档可能偏严**，广度测试里唯一的失误就是这个原因导致的，值得之后单独验证。
4. 耗时数据噪音很大，受那个已知的 gRPC 偶发慢问题影响严重，这次实验**没能得出"chunk_size 对耗时有什么影响"的可靠结论**。

## 六、这份实验的局限性（老实说）

- 样本量不算大：深度测试15题、广度测试4题/份，`temperature=0` 意味着同样的问题重复问多次结果不会变，所以想提高统计可信度，只能靠**增加不同的问题**，而不是重复问同一批题——这次没有进一步扩大样本。
- 只测了3组 `chunk_size`，区间比较粗（300/500/800），没有细化到比如600、700这种更精细的梯度，`800` 是不是"够用就好"还是"还能更大更好"，这次数据回答不了。
- 深度测试只用了一份文档（userA），"chunk_size 越大越好"这个结论，换一份篇幅/结构完全不同的文档（比如一份很短的、或者没有清晰段落结构的文档）是否依然成立，没有验证。

## 七、✅ 已采纳：默认值改为 800/80，并完成最终验证

根据上面的数据，把 `rag_pipeline.py` 的 `split_into_chunks()` 默认值从 `500/50` 改成了 **`800/80`**。改完用真实的默认调用方式（不手动传参，跟 `main.py`/`app.py` 完全一致的调用路径）把4份文档全部重新测了一遍：

| 文档 | chunk数（800/80下） | 正确率 |
|---|---|---|
| userA | 12 | **15/15（100%）** |
| 田中健一（厨师） | **1** | 4/4（100%） |
| 鈴木美咲（护士） | **1** | 3/4（75%） |
| 高橋大輔（广告营业） | **1** | 4/4（100%） |
| **合计** | | **26/27（96.3%）** |

对比改之前（500/50 下合计 25/27，92.6%），**准确率有实打实的提升**。

### 一个意外收获

那3份测试用假简历全文都不到800字，`chunk_size` 调到800之后，它们**自动变成了1个chunk**——不需要额外写"方案D（短文档不切）"的代码，调大 `chunk_size` 这一个动作就顺带把它实现了。

### 唯一剩下的失误，现在有了更干净的结论

鈴木美咲那题（"インシデント報告件数は前年比何パーセント削減しましたか"）还是没通过，但这次**整份文档本身就是1个chunk**，分数是 **0.8239**，还是卡在阈值 `0.8` 上方一点点。这证明了：**这不是"内容被切散"导致的问题**（已经没有切散的余地了，就一整块），纯粹是**这道题的问法和文档内容算出来的 embedding 相似度，刚好卡在阈值边缘**——印证了第三节提到的"阈值对短文档可能偏严"这个猜测，而且排除了 chunk_size 这个变量的干扰，结论更可信了。

# 第二部分：相关度阈值（`_RELEVANCE_THRESHOLDS`）

> 目的：验证"相关度阈值对短文档偏严"这个猜测，看能不能在不牺牲长文档"防止瞎编"这道保护的前提下，提升短文档的召回率。

## 背景

第一部分最终验证时发现：鈴木美咲那份简历（调完 `chunk_size=800` 后全文只有1个chunk）唯一答错的一题，检索分数是 `0.8239`，卡在阈值 `0.8` 上方一点点被拦截——这时候整份文档就是1个chunk，排除了"内容被切散"这个变量，证明问题出在阈值本身，不是chunk_size。

## 讨论过的思路

直接把 `google` provider 的阈值从 `0.8` 整体调大（比如调到 `0.85`），风险是**这是个全局参数**，放宽会让长文档的检索过滤也跟着变松，可能让更多"不够相关"的内容混进去，削弱"防止瞎编"这道保护——而且目前关于"不相关问题最高能把分数做到多低"的数据样本很少（只测过3个不相关问题，分数都在0.88-0.92，离0.8有安全距离，但不能代表所有情况）。

更有针对性的方向：**阈值感知"候选chunk数量"，而不是一个固定不变的全局数字**——chunk数量很少（比如≤2，相当于chunk_size调大之后的那些短文档）时，阈值放宽甚至跳过过滤；chunk数量多的长文档，阈值保持严格。理由：候选少的时候，"相关性过滤"本来筛选的候选面也小，起到的保护作用有限，而且 prompt 里本身设计了"没有答案就回答わかりません"这层LLM自己的兜底判断，双重保险下放宽这道关卡的风险较低。

## 实施方案

采纳了"阈值感知候选chunk数量"这个思路。`build_qa_chain()` 现在会记录整个向量库的总chunk数（`vector_store._collection.count()`），存进 `qa_chain["total_chunks"]`。`_retrieve_relevant_docs()` 检索时先判断：

```python
SMALL_DOC_CHUNK_THRESHOLD = 2

if total_chunks <= SMALL_DOC_CHUNK_THRESHOLD:
    # 候选少的短文档：跳过阈值过滤，检索到的内容直接交给LLM自己判断
    relevant_docs = [doc for doc, _ in results]
else:
    # 候选多的长文档：阈值过滤保持不变
    relevant_docs = [doc for doc, score in results if score <= score_threshold]
```

`SMALL_DOC_CHUNK_THRESHOLD = 2` 这个数字不是精确调出来的，是贴着"chunk_size=800之后，那3份测试短简历全部只有1个chunk"这个实际情况取的，留了一点余量（到2还生效）。

## 验证结果

**测试设计**：3份短简历（田中健一、鈴木美咲、高橋大輔，都是1个chunk）各测5题——4道原来就有的相关问题 + 1道新增的"不相关问题"（专门验证跳过阈值之后，明显不相关的问题还能不能被正确拒绝，这是之前没测过的场景）。

**结果：15/15（100%）全部正确。**

- **之前失败的那题终于答对了**：鈴木美咲"インシデント報告件数は前年比何パーセント削減しましたか" → 正确回答"前年比20%削減しました"
- **新增的3道不相关问题，全部被正确拒绝**：虽然跳过了阈值这道关卡，但 LLM 自己读完整份文档后，判断"答案不在里面"，照样回答"わかりません"——证明"阈值 + LLM自我判断"这套双重保险设计是有效的，拿掉其中一层，另一层依然能兜住

**结论**：针对"候选chunk数量少"这种场景，跳过阈值过滤是安全的、有实际收益的改动——既提升了短文档的召回率（修复了之前的误伤），也没有牺牲"防止瞎编"这道保护（LLM自己的判断补上了）。
