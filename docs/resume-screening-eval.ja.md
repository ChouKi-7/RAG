## 二、方法論

**期待値の決め方**：LLMが抽出した結果をそのまま信じるのではなく（それではシステムが自分自身を検証するだけで意味がない）、**履歴書の内容を書いた時点で自分が設定した原文**（プロジェクトの開始・終了日、原文の表現）から手で推算した「あるべき」結果を期待値とし、それをシステムの実際の出力と突き合わせた。

**事前に独立したチェックを実施**：エンドツーエンドのクエリを設計する前に、まず13件分の構造化抽出キャッシュ（`resume_profiles_cache.json`）を直接確認し、「スキルが正しく・漏れなく抽出されているか」と「`has_led_project`の判定が正しいか」の2点を、それぞれ設計意図と1件ずつ突き合わせた。

### 分析一（#3、実際のバグ、修正済み、詳細は [bug-log.ja.md #15](bug-log.ja.md)）

佐藤健太、小林翔太、井上陸の3名が最初に見逃された根本原因は、フィルタのロジックが間違っていたからではなく、**さらに上流の構造化抽出がこの3名のPython経験年数を少なく算出していた**ことにある（それぞれ0.5年、0.75年、0.5年と算出されたが、原文には「入社1年半」「入社2年目」「入社1年目」のような表現があり、本来は1年以上に近いはず）。

詳しく調べた結果、本当の根本原因を特定：**「表現が簡潔かどうか」ではなく、LLMが「本日」が実際いつなのか分からないこと**。見逃された候補者に共通するのは、最新または唯一の職歴が「2025年4月～現在」のような「現在」を含む開かれた期間であること。LLMはこの期間の終点が分からないまま計算するしかない。一方、正確だった候補者（渡辺大輝「8年」、加藤美月「7年」）は実はLLMが自分で計算したのではなく、要約文に書かれていた総年数をそのまま転記していただけだった。

**修正方法**：抽出用プロンプトに本日の日付（`datetime.date.today()`）を明示的に伝えた。修正後に再実行したところ、3名の年数は0.5/0.75/0.5から1.6/2.6/1.6へ正しく修正され、クエリ#3は3名見逃す状態から完全一致に変わった。

これはアーキテクチャ上の重要な教訓を示している：D12の設計にある「確定的なフィルタなら見逃しを保証できる」という主張には前提条件がある——**フィルタに渡される構造化データそのものが正確であること**。フィルタのロジック自体（`filter_by_structured_criteria()`）は「0.5 < 1なので除外」という判断を完全に正しく実行しており、間違っていたのはその判断材料（その0.5という数字）の方だった。

**修正の検証過程で見つかった新しい問題（bug#16として記録済み、未修正）**：この修正を検証している過程で、新たな問題も見つかった——松本さくらのJava経験年数が（たまたま正しかった）10.0年から13.6年に変わり、彼女が現在担当しているPM業務はJavaと無関係なのに、LLMがその期間の長さをJavaの総年数に誤って加算していた。この新しい問題を直そうと「帰属の制約」という一文を追加してみたが、逆効果だった（15.0へさらに悪化し、他の候補者の正しかったデータまで巻き込んで壊れた）——「プロンプトの一文を直して一回実行して様子を見る」というデバッグ方法は危険で、1回の実行で得られる「良くなった／悪くなった」は単なるノイズかもしれないことを示している。最終的に、その新しく追加した制約は撤回し、効果が確認できた「日付を伝える」という変更だけを残した。松本さくらのケースは既知の問題として記録し、**これ以上無理に直そうとはしなかった**。

### 分析二（#7、システムのバグではなく、今回のテスト設計自体の不備）

田中健一、鈴木美咲、高橋大輔というIT業界以外の3名が「余計に」一致判定された点は、一見誤判定に見えるが、彼らの履歴書の原文をよく見ると**実はこれが正しい挙動**だと分かる：

- 田中健一（シェフ）：「シェフ不在時は厨房全体の指揮を代行」
- 鈴木美咲（看護師）：「病棟内の業務改善プロジェクトのリーダーを歴任」
- 高橋大輔（広告営業）：「年間広告予算3億円規模のアカウントを管理」

これらの記述は確かに「何かを独立して担当・主導した」ことを述べており、ただ分野がIT業界ではないだけである。そして今回「プロジェクトを独立して担当できる人を探す」というクエリ自体には**分野の限定が一切なかった**ため、システムが彼らも条件を満たすと判定したのは論理的には正しい——**間違っていたのは、期待値を設計する際にIT業界の履歴書10件のことしか考えておらず、この非IT業界の履歴書3件の内容自体にも「独立して担当」に該当する記述が含まれていることを失念していた、こちら側の設計の方**だった。

この発見自体にも価値がある：`judge_qualitative()` の判定が本当に「意味が一致するかどうか」に基づいて行われており、候補者の業界がクエリの文脈（今回は全体としてIT採用の場面）と合わないからといって自動的に除外されるわけではない、ということを示している——「IT分野に限定して独立担当の経験を判定したい」のであれば、クエリ自体にその限定を明示する必要がある（例：「IT系プロジェクトで独立して担当できる人」）。これは**クエリ設計側の問題であり、システム実装のバグではない**。

## 六、総合結論

- **スキル識別**：13/13すべて正解で、現時点で問題は見当たらない（ただし「同義語・別名」のようなより難しいケースは、この13件の履歴書にはあえて設計しておらず、今回の評価範囲には含まれていない）
- **定性判定（独立担当かどうか）**：10/10正解、重要なネガティブケースを含めて、今回の評価範囲内では意味理解の信頼性は良好だった
- **経験年数の推定**：実際に影響範囲の広い本物のバグを発見・修正した（「現在」の日付が不確定なために広く過小評価が発生していた問題、bug#15として修正済み）が、修正の過程でさらに新しい、より厄介な問題（スキルとプロジェクトの紐付けの誤り、bug#16、**まだ未修正**）も見つかった。検討の結果「日付の修正は残し、この新しい問題は受け入れる」方が総合的に見てプラスだと判断した
- **エンドツーエンドのフィルタ＋判定**：1回目は8問中6問が一致、bug#15を特定・修正した後は7/8になった。残る1問（#7）は確認の結果テスト設計側の不備で、システムの欠陥ではなかった

**この評価は「システムに問題がないことを証明する」ためのものではなく、「どの部分で、どんな条件のときに問題が起きるか」を特定し、直せるところは実際に手を動かして直し、その過程で出た副作用も隠さず記録するためのもの**——それこそが評価のあるべき姿だと考えている。

## 七、`match_score`の専門評価（2026-11-24追加、[design-notes.ja.md D18](design-notes.ja.md)に対応）

D18で並び替え機能に`match_score`（0〜100）を追加したが、このスコアには「正解」が存在しない——経験年数のように履歴書の日付から逆算できる客観的な数字とは違い、「独立担当の度合いを何点にすべきか」自体がLLMの主観的な判断になる。そこで今回は視点を変えた：実在する候補者同士で「誰の点数が高いべきか」を比較するのではなく（主観的すぎて自己満足な検証になりかねない）、**強弱が誰の目にも明らかで曖昧さのない合成テキスト**を使い、2点を直接検証した：スコアが本当に強弱を区別できているか（弁別性）、同じ入力を繰り返しても結果が安定しているか（安定性）。

### テスト方法

同じ定性条件「プロジェクトを独立して担当できる」に対して、強度が段階的に下がる、意味が明確で曖昧さのない4つの文章を用意し、`judge_qualitative()` に直接渡した：

| ラベル | 文章 | 想定される強度 |
|---|---|---|
| A_最強 | 「要件定義・設計・実装・テスト・リリースまでの全工程を、一人で完全に担当した。」 | 最強 |
| B_中強 | 「リーダーの指示のもと、機能の設計の一部を担当し、自分で実装まで完成させた。」 | 中程度（やや強） |
| C_中弱 | 「先輩のサポートを受けながら、担当するよう割り振られた機能の実装を行った。」 | 中程度（やや弱） |
| D_最弱 | 「チームの一員として、指示された範囲のタスクをこなした。独自の判断は特に求められなかった。」 | 最弱 |

安定性テスト：A_最強の文章を、同じ条件で3回繰り返し実行し、スコアが一致するか確認した。

### テスト結果

**弁別性（4つの文章の実際のスコア）**：

| ラベル | match_score | matches |
|---|---|---|
| A_最強 | 100 | True |
| B_中強 | 30 | False |
| C_中弱 | 10 | False |
| D_最弱 | 0 | False |

単調減少（A≥B≥C≥D）：**成立**。さらに`matches`という真偽値も注目に値する——B_中強は30点と0点ではなかった（LLMが「自分で実装まで完成させた」という部分に一定の独立性を認めたことを示す）が、それでも`matches=False`と判定されており、「少しでも当てはまれば合格」という甘い基準にはなっていないことが分かる。

**安定性（A_最強を3回繰り返し）**：100、100、100、**完全に一致**。

### 結論

- `match_score`は適当に付けているわけではない——4つの文章の強度が下がるにつれてスコアも下がっており、区別が明確（100→30→10→0）で、「とりあえず70〜80点」のような曖昧な付け方ではない
- `temperature=0`は実際に出力の安定化に寄与しており、同じ入力を繰り返してもスコアがぶれない——これは、並び替えの結果が「同一セッション内では」信頼でき、再現可能であることを意味する
- **以前発見した「候補者9名中3名が同点100点」という現象**（[resume-screening-notes.ja.md の既知の限界](resume-screening-notes.ja.md)参照）を振り返ると：今回のテストは「それらの候補者の証拠の強さが、もともとA_最強と同程度のレベル（例：『一人で立ち上げから運用まで担当』『基盤刷新を独力で完遂』のような表現）だったから」という説明を裏付ける新たな根拠になった——採点の仕組みそのものが機能していない、あるいはいい加減に付けているわけではない、という点については懸念をほぼ払拭できた。ただし「同じ階層で並んだときの内部順序には根拠がない」という限界自体は依然として残っている（D18に記録済み、解決の予定なし）
