# 複数履歴書スクリーニング機能（v2）ノート

> 対応コード：[resume_screening.py](../resume_screening.py)
> このドキュメントは「この機能がどう動くか」を説明する。設計上の「なぜこうしたか」の要約は [design-notes.ja.md D12〜D18](design-notes.ja.md) を、
> 単一文書問答(v1)のコード解説は [project-notes.ja.md](project-notes.ja.md) を、精度評価のデータと分析は [resume-screening-eval.ja.md](resume-screening-eval.ja.md) を参照。

## 一、この機能が解決する課題

v1でできるのは「1つの文書に対する持ち込み可の質問応答」。しかし「5件の履歴書の中で、Pythonを3年以上学び、かつプロジェクトを独立して担当できる人は誰か」という質問は、本質的に**複数文書にまたがる条件スクリーニング**であり、「最も関連する断片を検索する」のとは違う問題——v1のベクトル検索の発想でそのままやろうとすると、2つの問題にぶつかる：

1. **網羅できない**：検索は「最も類似した上位k件」しか返さず、条件に合う人を全員見つける保証がなく、見逃しが起きやすい
2. **経験年数のような情報はチャンク分割で壊れる**：「この人がJavaを何年使ったか」は複数のプロジェクトに分散した日付区間を合算して算出する必要があり、どこか一箇所に直接答えが書いてあるわけではない。履歴書をチャンクに分割してしまうと、こういう「全文を見て初めて算出できる」情報は確実に抽出できなくなる

そのためv2ではv1のChromaベクトルDBを再利用せず、別のパイプラインを新設した：まず各履歴書を構造化データに「読み替え」、スクリーニングは構造化フィールドの厳密な一致で行い、判断が難しい部分だけLLMに1人ずつ再確認させる。

## 二、3段階の処理フロー

### 第1段階：インデックス作成——履歴書を構造化データに読み替える（`build_candidate_profiles()`）

各PDFに対して：

```python
full_text = load_resume_text(path)              # チャンク分割せず全文をテキスト化
profile = extract_candidate_profile(full_text, llm)  # LLMで構造化フィールドに抽出
```

抽出には `pydantic.BaseModel` で定義したスキーマを使い、`llm.with_structured_output()` で出力形式を強制する。プロンプトで「できるだけJSONで出して」と頼る方式ではない：

```python
class SkillExperience(BaseModel):
    skill: str
    years: float   # LLMがプロジェクトの日付から逆算した値。履歴書に直接書かれた数字ではない

class CandidateProfile(BaseModel):
    candidate_name: str
    skills: list[SkillExperience]
    has_led_project: bool
    leadership_evidence: str | None   # 上記判断の根拠となる原文の抜粋
```

抽出結果は**ファイル内容のハッシュをキーにキャッシュ**する（`resume_profiles_cache.json`）。履歴書の内容が変わらなければ再度LLMを呼ばない——v1の「既存のベクトルDBがあればそのまま読み込む」という考え方と同じ（API無料枠の節約）。

### 第2段階：クエリ理解——自然言語の質問を構造化条件に解析する（`parse_query()`）

ユーザーが「Pythonを3年以上学び、プロジェクトを独立して担当できる人を探す」と入力すると、同じ仕組みで次のように解析される：

```python
ScreeningQuery(skill="Python", min_years=3.0, qualitative_criteria="プロジェクトを独立して担当できる", limit=None)
```

`limit`（2026-11-24追加）は質問に含まれる件数指定（「2人」「上位3件」など）。指定がなければ`None`。

### 第3段階：二段階の絞り込み

**まず構造化フィルタ**（`filter_by_structured_criteria()`。純粋なPythonロジックで、LLMを呼ばない）：

```python
candidate_years = matching_skill.years  # そのスキルにヒットした
if candidate_years < query.min_years:
    continue  # 年数が足りないので除外
```

この段階はLLMに頼らないため結果が決定論的で、単体テストで検証できる（[tests/test_resume_screening.py](../tests/test_resume_screening.py) 参照）。「気分次第で見逃す」ということが起きない。

**残った候補者に対して定性的な再確認**（`judge_qualitative()`）：ひとりひとりについて、履歴書全文と「プロジェクトを独立して担当できる」という定性条件を一緒にLLMに渡し、判断理由と**原文の引用**を出力させる。「はい／いいえ」だけを出させない：

```python
class QualitativeJudgement(BaseModel):
    matches: bool
    match_score: int   # 0〜100、2026-11-24追加、結果の並び替えに使う
    reason: str
    evidence_quote: str | None
```

この2段階をまとめたのが `screen_candidates()`：構造化条件でまず範囲を絞り（候補者が多いときのLLM呼び出し数を節約）、定性条件で精密に絞り込む。結果には「なぜその人が選ばれたか」の根拠が付いており、ブラックボックスの結論ではない。

### 第4段階（2026-11-24追加）：並び替え＋件数指定（`_rank_and_limit()`）

以前はスクリーニング結果が順不同で、「Javaの経験がある人を2人教えて」のような件数指定のある質問に答えられなかった。現在は `screen_candidates()` が結果を返す前に、もう一段処理を加えている：

- **定性条件がある場合**：`judge_qualitative()` が付けた `match_score` の高い順に並べる——判定のときについでに出力させているだけなので、追加コストはゼロ
- **定性条件がない場合**：既に抽出済みのスキル経験年数が長い順に並べる——これも追加のLLM呼び出しはなく、既にある数字を再利用するだけ
- 並び替えた後、`query.limit` に値があればその件数に切り詰める

この順序（先に並び替え、その後に切り詰める）は意図的なもの——「上位2件」が本当に「最もマッチ度の高い2件」になることを保証し、「適当な2件」にならないようにしている。

## 三、実測で踏んだ落とし穴

情報量の多い履歴書（4件のテスト履歴書のうち、情報が最も密な本物の履歴書だけで発生）に対して、`with_structured_output()` が**エラーも出さず黙って`None`を返す**ことがあった——根本原因は、長いコンテキストの場合にモデルが「関数呼び出し」を使わず、JSONを通常のテキスト回答に包んで返すことがあるため。`_invoke_structured()` というラッパーでフォールバック解析を実装した（まず通常のパースを試み、失敗したらテキストから正規表現でJSONを抜き出す）。詳しい経緯は [bug-log.ja.md #12](bug-log.ja.md) に記載。

## 四、使い方

**CLI版**：

```bash
python resume_screening.py
```

`documents/` 配下のすべてのPDFをスキャンする（v1の`main.py`が最初の1件しか使わないのとは違う）。各ファイルに構造化インデックスを作成した後、質問応答ループに入り、連続して複数のスクリーニング条件を質問できる。`exit`で終了。

**Web版**（2026-11-18追加、`resume_screening_app.py`）：

```bash
streamlit run resume_screening_app.py --server.port 8502
```

v1の`app.py`と同じ構造（同じパスワードゲート、`st.chat_input`を使ったチャット形式のやり取り）だが、`accept_multiple_files=True`で複数PDFを一度にアップロードできる点が違う。v1にはなかった設計上のポイントが1つある：**ブラウザセッションごとに独立した一時キャッシュファイルを使う**ことで、`resume_screening.py`のCLI版がデフォルトで使う`resume_profiles_cache.json`を共有しない。これはv1の [bug-log.ja.md #8](bug-log.ja.md) の二の舞を避けるための設計（当時はChromaの`collection_name`がセッションごとに分かれておらず、異なるユーザーがアップロードした文書の内容がベクトルDB内で混線した）。今回はベクトルDBではなくローカルのJSONファイルだが、「異なる訪問者のデータは互いに隔離されなければならない」という原則は同じなので、問題が起きてから直すのではなく、最初からセッション単位で分離してある。

## 五、現時点の限界（正直に書く）

- ~~スキル名のマッチングが粗い~~（**部分文字列の誤判定は2026-11-10に修正済み、同義語は2026-11-18に部分対応**）：以前は大文字小文字を区別しない部分一致で、「Java」で検索すると「JavaScript」にもマッチしてしまっていた——専用に用意したIT業界テスト履歴書10件で実測再現した後、単語境界でのマッチング（`_skill_matches()`、[design-notes.ja.md D14](design-notes.ja.md)、[bug-log.ja.md #14](bug-log.ja.md) 参照）に変更した。同義語・別名（「機械学習」と「ML」など）には、その後embeddingの類似度によるフォールバックを追加した（単語境界で一致しない場合に、2つの単語のベクトル類似度を計算し、しきい値を超えれば一致とみなす、[design-notes.ja.md D17](design-notes.ja.md) 参照）——ただし**これは「部分対応」であり「解決」ではない**：実測で「Go/Golang」「JS/JavaScript」のような同義語は拾えることを確認したが、「ML/機械学習」「AWS/Amazon Web Services」のように文字面が大きく異なる略語はまだ拾えない。しきい値を下げると今度はbug#14が復活してしまうため、両方を同時には満たせない
- ~~体系的な精度評価がまだない~~（**2026-11-17に一度完了し、見つかった主な問題も修正**）：スキル識別13/13正解、定性判定（独立担当かどうか）10/10正解で重要なネガティブケースも含む。経験年数の推定では最初「タイトルに簡潔に触れられているだけ／複数プロジェクトの合算が必要なケースで明らかに過小評価される」問題が見つかり（根本原因はLLMが「本日」を知らないこと）、抽出用プロンプトに本日の日付を明示的に渡すことで修正した——ただし**その修正の検証過程で、新しい未解決の問題も見つかった**：一部の候補者で、あるスキルと全く無関係なプロジェクトの期間がそのスキルの年数に誤って加算されてしまう（紐付けの誤り）。この新しい問題は現時点で**未修正**（[bug-log.ja.md #16](bug-log.ja.md) として記録済み。「日付の修正は残し、この新しい問題は受け入れる」方が総合的にプラスと判断した）。方法論・データ表・分析の全体は専用の評価ドキュメント [resume-screening-eval.ja.md](resume-screening-eval.ja.md) を参照
- ~~候補者数が増えたときのコストが未検証~~（**2026-11-10、一部検証済み。新たな問題も発覚**）：履歴書14件（既存4件＋新規生成のIT業界テスト履歴書10件）でテストした結果、候補者数が多く、スキル・年数のような構造化フィルタが効かない質問だと、LLM呼び出しが短時間に集中し、Geminiの無料枠「1分あたり15リクエスト」の制限に実際にぶつかることが判明（[bug-log.ja.md #13](bug-log.ja.md)）。リトライで対処済みだが、**遅延・コストの定量データ**はまだない——「制限に当たっても自動で待ってリトライする」ことと「速くて安い」ことは別の話
- **並び替え結果の同点スコア**（2026-11-24に発覚、同日に採点メカニズム自体は専門検証で問題なしと確認）：定性判定は候補者ごとに独立して採点しているため、「明らかに当てはまる」候補者が同点の最高スコアになりやすい（実測では9名中上位3名が全員100点）。同点同士の前後関係は現状、候補者リストの元の順序に依存しており、本当の優劣を表していない——これは「独立して採点する」という設計に内在する副作用。詳細は [design-notes.ja.md D18](design-notes.ja.md) を参照。強弱に異論の余地がない合成テキストで弁別性・安定性を専門にテストした結果（[resume-screening-eval.ja.md 七](resume-screening-eval.ja.md)参照）、採点メカニズム自体は信頼できることを確認した（強度が下がる4つの文章でスコアも下がり、同じ入力を3回繰り返しても完全に一致）——**同点になるのは証拠の強さがもともと近いレベルだったからで、採点が手抜きなわけではない**。ただし「同じ階層で並んだときの内部順序に根拠がない」という限界自体は未解決のまま
